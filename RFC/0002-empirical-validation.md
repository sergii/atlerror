# RFC 0002: Empirical Validation Layer

- Status: Draft
- Scope: Reproducible validation of diagnostic claims

## Summary

Atlerror should distinguish semantic knowledge from empirical support.

A hypothesis is a candidate explanation. A claim is a concrete, testable statement derived from a hypothesis. An experiment is a reproducible procedure that tests one or more claims. Empirical evidence is the result of one concrete run in a declared environment.

The project must avoid treating a successful synthetic experiment as universal proof. Results use `supports`, `contradicts`, or `inconclusive`.

## Core types

### Claim

A stable, machine-addressable diagnostic assertion.

A claim should:

- reference a hypothesis;
- define one or more predicted observations;
- be narrow enough to test;
- state runtime/environment scope when relevant;
- record important limitations.

Example:

```text
claim.memory.retention.live_set_and_rss_grow
```

### Experiment

A reproducible procedure that tests claims.

The initial runner contract is intentionally small and Docker-based:

```text
experiment manifest
  -> generic lab runner
  -> Docker build
  -> controlled intervention
  -> evidence JSON on stdout
  -> schema validation
  -> expected-result check
```

Experiment manifests describe orchestration. Fixture code describes the physical mechanism under test.

### EmpiricalEvidence

A concrete run result containing:

- experiment ID;
- claim IDs;
- runtime and platform provenance;
- measured observations;
- assertions;
- result classification;
- interpretation;
- limitations.

Evidence artifacts are generated by CI and are not automatically promoted to universal truth.

## Invariants

1. A hypothesis may exist without empirical validation.
2. A claim must reference an existing hypothesis and existing observations.
3. An experiment must reference existing claims.
4. An evidence result must reference the experiment and claims that produced it.
5. The generic runner validates all contracts before accepting a lab result.
6. A passing CI experiment means the declared claim was reproduced in the declared environment, not that all production instances behave identically.

## Human and agent use

For humans, empirical evidence should eventually appear next to explanations as reproducible support and teaching material.

For agents, claims and experiments make diagnostic knowledge operational: an agent can understand what observation is predicted, whether a known synthetic reproduction exists, and how strong the available evidence is.

## Initial implementation

The first two empirical claims are:

- retained Ruby objects increase the post-GC live set and process RSS;
- a Ruby busy loop can consume close to one CPU core while spending most CPU time in user space.

Both run through the same generic Docker lab contract.

## Future work

- aggregate evidence across repeated runs;
- evidence IDs and immutable provenance records;
- cross-runtime experiment matrices;
- literature and production-case evidence sources;
- statistical confidence and flakiness handling;
- cost-aware lab selection;
- privileged/eBPF and VM experiment tiers;
- website rendering of evidence and limitations.
